# Investigation: Alembic + ORM integration (Engine Room)

**Date:** 2026-07-29  
**Scope:** Family Edu Engine Room (`engine-room/`)  
**Current state:** Raw `aiosqlite` + custom `db/migrate.py` + SQL files in `db/migrations/`

---

## 1. Executive recommendation

| Option | Verdict |
|--------|---------|
| **A. Keep custom SQL migrator** | **Recommended now** — production-ready, zero new deps, already wired to startup/CI/deploy |
| **B. Alembic + SQLAlchemy Core only** | Optional later if you want autogenerate without full ORM rewrite |
| **C. Full SQLAlchemy 2.0 ORM + Alembic async** | Only when the data layer grows (Postgres, multi-dev schema churn, complex relations) |

**Do not** drop the current migrator until a dual-run period proves Alembic applies the same schema on a copy of production data.

## 2. Current architecture

```
engine-room/db/
  sqlite.py          # Fernet tokens, profiles, lessons (hand-written SQL)
  migrate.py         # Versioned *.sql runner → schema_migrations table
  migrations/
    001_initial_schema.sql
    002_system_settings.sql
    003_assignment_cache.sql
```

- **No SQLAlchemy / Alembic** in `requirements.txt` today.
- `DATABASE_URL` already uses the SQLAlchemy-style form `sqlite+aiosqlite:///./engine_room.db` (path is parsed manually).
- Startup: `lifespan` → `init_db()` → `migrate_up()`.
- CI/deploy already call `python -m db.migrate`.

### Strengths of current approach

- Explicit SQL (easy to review in PRs)
- No autogenerate surprises on SQLite
- Works offline, Windows-friendly
- Transactional apply + rollback on failure
- Idempotent `CREATE IF NOT EXISTS` baseline for legacy DBs

### Gaps

- No **autogenerate** from models
- No **downgrade** path
- No first-class **branching** / dependency graph (Alembic revisions)
- Schema is not expressed as Python models (drift risk if someone edits `sqlite.py` SQL only)

## 3. What Alembic actually requires

Alembic is built around **SQLAlchemy** metadata:

1. **SQLAlchemy** models or `Table` objects → `MetaData`
2. **Alembic** compares DB vs metadata (autogenerate) or runs revision scripts
3. For async apps: `alembic init -t async` and `create_async_engine("sqlite+aiosqlite://...")` with `connection.run_sync(...)`

Alembic does **not** replace an ORM by itself. Without SQLAlchemy, you only get a heavier runner for the same SQL files you already have.

### Async note (official pattern)

```python
# Conceptual — Alembic async template
async with connectable.connect() as connection:
    await connection.run_sync(do_run_migrations)
```

SQLite + `aiosqlite` is supported via SQLAlchemy’s async dialect. For SQLite **ALTER** limitations, enable **batch mode**:

```python
context.configure(..., render_as_batch=True)  # critical for SQLite column changes
```

## 4. Integration options compared

### Option A — Status quo (custom migrator)

| Pros | Cons |
|------|------|
| Already shipped | Manual SQL only |
| Minimal deps | No downgrade |
| Fits family-scale schema | Less standard for large teams |

**Effort:** 0  
**Risk:** Low

### Option B — Alembic running existing SQL (thin wrapper)

- Keep `001_*.sql` as the source of truth
- Alembic revisions that only `op.execute(open("...").read())`
- Still no ORM

| Pros | Cons |
|------|------|
| Standard CLI (`alembic upgrade head`) | Dual bookkeeping (`schema_migrations` vs `alembic_version`) |
| Easier hire familiarity | Little gain over current runner |

**Effort:** Medium  
**Risk:** Medium (two version tables if not careful)

### Option C — SQLAlchemy 2.0 ORM + Alembic (full)

Add dependencies:

```text
sqlalchemy>=2.0.36
alembic>=1.14.0
# aiosqlite already present
```

Introduce:

```
engine-room/db/
  base.py          # DeclarativeBase, create_async_engine, async_sessionmaker
  models.py        # Token, Profile, Conversation, Lesson, SystemSetting, ...
  alembic.ini
  alembic/
    env.py         # async template + render_as_batch=True
    versions/      # autogenerated revisions
```

Rewrite `sqlite.py` data access to use `AsyncSession` (or keep raw SQL alongside during transition).

| Pros | Cons |
|------|------|
| Autogenerate migrations | Large refactor of token/profile/lesson code |
| Type-safe models | SQLite batch migrations still fiddly |
| Path to Postgres | Learning curve; more moving parts |
| Industry default for FastAPI | Overkill for current table count (~6–8) |

**Effort:** High (several days)  
**Risk:** High if done in one shot on production DB

## 5. Mapping current tables → ORM (if Option C)

| Table | Suggested model | Notes |
|-------|-----------------|-------|
| `tokens` | `Token` | Encrypted strings stay `Text`; encryption stays in service layer |
| `profiles` | `Profile` | PK `google_user_id` |
| `conversations` | `Conversation` | Index on `google_user_id` |
| `lessons` | `Lesson` | JSON blob column or JSON type |
| `system_settings` | `SystemSetting` | key / value_json |
| `system_events` | `SystemEvent` | append-only |
| `assignment_cache` | `AssignmentCache` | composite PK `(user_id, id)` |
| `schema_migrations` | — | Replaced by Alembic’s `alembic_version` |

Fernet encryption should **remain outside** the ORM (encrypt before write, decrypt after read) — do not put keys in model defaults.

## 6. Migration path from current → Alembic (safe sequence)

If you choose Option C later:

1. **Freeze** custom SQL: no new `004_*.sql` except critical hotfixes.
2. Add SQLAlchemy models that **exactly** match live schema (introspect production DB).
3. `alembic init -t async alembic`
4. Set `render_as_batch=True` for SQLite.
5. Stamp existing DBs without re-running DDL:

   ```bash
   alembic stamp head   # after baseline revision that mirrors 001–003
   ```

6. Dual-run: CI applies both custom migrator (no-op) and `alembic upgrade head` on empty DB; assert identical `sqlite_master`.
7. Switch `init_db()` to `alembic upgrade head` (programmatic or subprocess).
8. Remove `db/migrations/*.sql` only after one full release cycle.

**Never** run autogenerate against production without reviewing the script.

## 8. Decision matrix

**Stay on custom migrator if:**

- Schema changes are rare
- You want minimal dependencies on Windows family laptops
- Current CI/deploy path is enough

**Adopt Alembic+ORM when:**

- You move to **Postgres** or multiple environments with frequent schema edits
- Multiple developers ship DB changes weekly
- You need downgrade/rollback scripts as policy

## 10. Conclusion

Alembic is the right long-term tool **if** the Engine Room becomes a multi-service, multi-dev data plane. For the current Family Edu System, **Alembic is optional**, not blocking production.

**Recommended next step:** keep `db/migrate.py`; when the first Postgres target or third concurrent backend developer appears, execute §6 (stamp + dual-run) rather than a big-bang rewrite.
